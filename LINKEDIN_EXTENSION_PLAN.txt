LINKEDIN CHROME EXTENSION PLAN - Resume Parser Auto-Population

TL;DR
Build a Chrome extension that extracts candidate data from LinkedIn profiles (Name, Email, Phone, Experience, Education, Skills) and safely auto-populates into your Resume Parser API. Use DOM parsing to avoid IP blocks (SignalHire strategy). Key: 50 submissions/day limit + 3-5 second delays between requests.

================================================================================
PHASE 1: CORE EXTENSION (WEEK 1)
================================================================================

1. Create manifest.json (v3) with LinkedIn profile permissions
2. Build content.js (LinkedIn DOM parser) to extract visible data:
   - Name, Title, Location from profile header
   - Work experience (loop through experience cards, extract title/company/dates)
   - Education & Skills sections
3. Create popup.html/js (UI) to preview extracted data with "Extract" & "Auto-Populate" buttons
4. Build background.js (Service Worker) to store JWT token from Resume Parser
5. Test on 5 LinkedIn profiles manually

================================================================================
PHASE 2: API INTEGRATION & ANTI-BLOCKING (WEEK 2)
================================================================================

1. Implement JWT authentication flow (popup login screen)
2. Add rate limiting: 50 submissions/day per HR user (prevents LinkedIn's "50 actions/24h" block)
3. Add request throttling: 3-5 second minimum delay between submissions
4. Call Resume Parser's PATCH /candidates/{id} endpoint with extracted data
5. Implement exponential backoff on API errors (5s → 10s → 20s if fails)
6. Log submission history in extension storage
7. Test 50 sequential submissions, verify no LinkedIn blocks

================================================================================
HOW TO AVOID LINKEDIN IP BLOCKS
================================================================================

Strategy 1: DOM Parsing Only
- Parse visible profile HTML instead of API calls
- LinkedIn doesn't see bot behavior
- Result: No blocking

Strategy 2: 50/day Limit
- LinkedIn allows ~50 significant actions/24h
- Cap extension at 50 submissions/day
- Prevents automated detection

Strategy 3: Request Delays
- 3-5 seconds between submissions
- Spreads load (not machine-like rapid-fire)
- Appears human behavior

Strategy 4: Browser Extension
- Runs in authenticated user session (not headless bot)
- Legitimate Chrome manifest
- Same IP as human user

Strategy 5: Rotating User Agents
- Different browser signatures per request
- Minor security bonus

Strategy 6: Exponential Backoff
- If Resume Parser returns error, wait longer before retry
- Not hammering = not bot-like

KEY INSIGHT: SignalHire works because it uses DOM parsing + low frequency, NOT API scraping.

================================================================================
ARCHITECTURE COMPONENTS
================================================================================

manifest.json (v3):
- Permissions: activeTab, scripting, storage, webRequest, alarms
- Matches: https://www.linkedin.com/in/* (LinkedIn profile URLs only)
- Host permissions: Your Resume Parser API domain
- Background Service Worker: background.js
- Icons: 16, 48, 128 pixels

content.js (LinkedIn page injection):
- Inject listener when user lands on /in/{profile-name} URL
- Parse DOM for: Name, Email, Phone, Work history, Education, Skills
- Send extracted data to popup as message
- Status indicator badge on page

popup.js (UI):
- Display extracted candidate data in popup
- Show preview with fields: Name, Email, Phone, Experience (count), Education, Skills
- Buttons: "Auto-Populate", "Edit & Save", "View in App"
- Status: "Parsing...", "Ready", "Sending...", "Success", "Error"
- Rate limit indicator: "Requests today: X/50"

background.js (Service Worker):
- Manage JWT token (store in chrome.storage.local, refresh at expiry)
- Rate limiting: Track daily request count per HR user
  - Limit: 50 candidates/day per user
- Request queue with exponential backoff
- Handle retries on 429 (Too Many Requests)
- Listen for extraction messages from content.js

================================================================================
DATA EXTRACTION STRATEGY
================================================================================

Approach 1: DOM Parsing (RECOMMENDED - No blocking)

const name = document.querySelector('[data-test-id="profile-top-card-profile-name"]')?.textContent;
const title = document.querySelector('[data-test-id="top-card-headline"]')?.textContent;
const location = document.querySelector('[data-test-id="top-card-headline"] span')?.textContent;

// Experience section
const experiences = Array.from(document.querySelectorAll('[data-test-id="profile-experience-item"]'))
  .map(el => ({
    title: el.querySelector('[data-test-id="profile-experience-section__title"]')?.textContent,
    company: el.querySelector('[data-test-id="profile-experience-section__company-name"]')?.textContent,
    dates: el.querySelector('[data-test-id="profile-experience-section__start-date"]')?.textContent
  }));

// Skills
const skills = Array.from(document.querySelectorAll('[data-test-id="profile-skills-section"] li'))
  .map(li => li.textContent.trim());

Email/Phone Extraction:
- Public Display: If user shared email on headline
- LinkedIn's "Open to Work" cards: May contain email
- Fallback: Suggest user add email/phone to "Contact Info" section
- Disclaimer: "Email/Phone must be public on your LinkedIn profile"

================================================================================
KNOWN RISKS & MITIGATIONS
================================================================================

Risk: LinkedIn changes DOM structure
Severity: HIGH
Mitigation: Content.js must be updated quarterly; use data-test-id selectors (more stable)

Risk: User exceeds rate limit
Severity: MEDIUM
Mitigation: Daily cap with UI warning; suggest next-day retry

Risk: JWT token expires mid-submission
Severity: MEDIUM
Mitigation: Auto-refresh token before API call; catch 403 and retry

Risk: Email/Phone unavailable on profile
Severity: MEDIUM
Mitigation: Mark as optional fields; show UI disclaimer before extraction

Risk: IP block from LinkedIn
Severity: LOW (with strategy)
Mitigation: Rate limiting + DOM-only parsing prevents; if occurs, user waits 24h
